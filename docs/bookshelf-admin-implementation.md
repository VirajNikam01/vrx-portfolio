# Bookshelf management

The private workspace starts at `/admin`, with login at `/admin/login` and collection management at `/admin/bookshelf`. It supports all six media types, personal Markdown notes, cover/source URLs, tags, editorial order, private previews, publication, hiding, and book/course chapter management. Content saves directly to the existing tables; routine editing requires no seeds or deployment.

Administration is now a shared module workspace rather than a Bookshelf-specific shell. Feature flags are editable at `/admin/settings/feature-flags`. Navigation, sessions, API transport, unsaved-change protection, and cache refresh are shared; data writes remain in their table's owner service/repository. See [the module architecture](admin-architecture.md) for boundaries and extension guidance. Migration 0012 adds versioned, field-preserving updates to the existing content configuration row.

## Owner configuration

The requested owner email and initial password have been configured in the local, Git-ignored `.env`. Only the password hash is stored there. No default password is shipped in application code or documentation, and absent/invalid configuration prevents login.

Private server variables:

- `ADMIN_EMAIL`: owner email, compared after trimming and case normalization.
- `ADMIN_PASSWORD_HASH`: salted scrypt hash generated by the supplied script. Its colon-separated representation avoids environment-variable expansion of hash delimiters.
- `ADMIN_CREDENTIAL_VERSION`: generated rotation value; changing it, the email, or the password hash invalidates previous sessions after the server restarts.
- `ADMIN_ORIGIN`: set to the site's exact HTTPS origin on deployments behind a proxy. Local development can omit it and use the incoming request origin.
- `DATABASE_URL`: existing PostgreSQL connection configuration.

To replace the password locally in PowerShell:

```powershell
Read-Host -MaskInput 'New admin password' | node scripts/admin-password.mjs
```

Restart the server afterward. The script updates the private hash and credential version without writing a plaintext password to a file or passing it as a command-line argument. Configure the corresponding private server environment variables separately when deploying; local `.env` files are not committed or deployed automatically. Do not use `NEXT_PUBLIC_*` variables for these values.

## Authentication and writes

- Node's maintained scrypt implementation verifies the configured password with a timing-safe comparison.
- Opaque eight-hour sessions use random 256-bit tokens. Only SHA-256 token hashes, credential versions, and expiration dates are stored in `admin_sessions`.
- Cookies are HttpOnly, SameSite Strict, host-only, and Secure on HTTPS. Logout removes the database session as well as clearing the cookie.
- `admin_login_limits` provides atomic persistent account/IP attempt windows. Five unsuccessful attempts block further attempts until the 15-minute window expires. Successful logins clear the relevant buckets. A global owner bucket remains effective even without a trusted IP header.
- Every protected server page and admin API checks the session. Mutations require a matching Origin, JSON content type, and a non-simple custom request header; no cross-origin access is enabled.
- Admin responses are private/no-store/noindex. Public lists, direct links, topic routes, and sitemaps continue applying visibility rules.
- Input contracts reject unexpected properties and unsafe source URLs. Private previews and public notes rendering disable raw HTML.
- Published slugs remain locked after hiding. New drafts and topics are explicitly unpublished; existing database defaults cannot publish a new editor record accidentally.
- Integer versions implement optimistic concurrency. A stale save returns 409, leaving the form intact. Unique URL errors identify the slug field.
- The recommendations owner opens a transaction and locks its parent row. Topic operations and type-dependency checks run through their respective owner services/repositories using that transaction, preventing a topic creation/type change race without crossing table ownership boundaries.
- Successful saves invalidate collection, item, legacy detail/topic, admin, and sitemap paths. Fresh public reads see publication changes without a build. Existing open public tabs can be refreshed.

## Editing behavior

Save draft persists privately; Publish validates and makes the item visible. Save changes on an already published item is an immediate public update. Hide and Unpublish are reversible and retain all content. There is no permanent deletion UI.

Draft preview stays within the authenticated editor. Covers use URL input and the shared artwork fallback; file uploads are deferred. Published book/course items can keep their existing chapter notes and URLs.

Failed and conflicting saves retain entered values. Expired-session errors offer a sign-in link in another tab so the original form can be saved afterward. Unsaved edits warn on normal link navigation, logout, and browser close/refresh where supported. There is no autosave or full revision-history workflow.

## Database migration

The configured database's pre-existing schema was checked against migration snapshot 0010: column types/nullability/defaults, indexes, unique constraints, foreign keys, primary keys, and enum values. Its existing topic foreign key had equivalent semantics under an older name; only the constraint name was aligned. Migration records 0008–0010 were then reconciled without replaying table creation.

Migration 0011 adds the two auth tables, item/topic version numbers, and persistent published-slug locks. Existing visible/published rows were marked URL-locked. Existing content was preserved.

For this checkout's known baseline, the verified reconciliation/migration helper can be run with:

```powershell
node --env-file=.env scripts/migrate-bookshelf-admin.mjs
```

It refuses unexpected or incompatible baselines. Once reconciled, normal subsequent Drizzle migrations can proceed. Never mark an unrelated database as migrated without inspecting its schema.

## Verification

Focused tests cover password verification, generic login errors, persistent throttling, token hashing, credential rotation, session expiry predicates, unauthenticated access to every content endpoint, CSRF rejection, validation, publication/URL locks, stale writes, topic dependencies, cross-parent access, and timestamp serialization.

Live browser tests in `tests/e2e/bookshelf-admin.spec.ts` use the configured owner credentials through private environment variables. They create only disposable hidden drafts, verify reload/private preview/chapter editing and retained errors, and remove their own fixtures afterward. They do not publish sample content or modify existing owner content. Responsive screenshots cover 320, 768, and 1440 pixels in light/dark modes.

Set `ADMIN_TEST_PASSWORD` privately for these browser tests; do not put it in the test source, traces, or tracked configuration. The existing broader suite has known resume-dialog and experience assertion failures that are unrelated to this workspace.
